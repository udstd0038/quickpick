# QuickPick 开发工作流

## 1. 每次开发开始前

必须先做：

- 阅读 `CLAUDE.md`。
- 阅读与本次任务相关的 `docs/` 文件。
- 查看当天开发日志是否存在。
- 确认本次只做一个小阶段或一个明确子任务。

如果任务范围过大，应先拆分，不要一次性做太多。

## 2. 每次开发中

执行原则：

- 先了解现状，再修改。
- 优先遵循现有结构。
- 不引入与本阶段无关的大依赖。
- 不做顺手重构。
- 不实现未进入 MVP 的功能。
- 复杂系统调用要有最小可验证用例。

文件修改原则：

- 文档修改保持中文。
- 代码文件按项目技术栈规范执行。
- 不把敏感数据写入仓库。
- 不提交 API Key、截图内容、AI 响应全文。

## 3. 每次开发结束前

必须完成：

- 运行适合本阶段的检查或说明无法运行的原因。
- 若本次修改影响应用代码、配置、资源或发行产物，覆盖默认 release 后自动启动 `src-tauri/target/release/quickpick.exe`，方便用户直接验收新版。
- 更新 `dev-logs/YYYY-MM-DD.md`。
- 写明今日完成、待办、关键决策、问题、验证结果、下次建议。
- 如果修改了需求、架构、设计、安全或测试规则，同步更新对应 `docs/` 文件。

## 4. 开发日志格式

每日日志使用以下结构：

```markdown
# YYYY-MM-DD 开发日志

## 今日完成

- ...

## 今日待办

- ...

## 关键决策

- ...

## 遇到问题

- ...

## 验证结果

- ...

## 下次建议

- ...
```

## 5. 小步推进标准

一个合格的小阶段应满足：

- 目标清楚。
- 文件范围有限。
- 能被测试或检查。
- 完成后项目状态更稳定。

不合格的阶段例子：

- “把所有功能都做完。”
- “顺便重构所有架构。”
- “先加一堆库以后可能用。”

## 6. 文档优先级

发生冲突时按以下顺序判断：

1. 用户最新明确要求。
2. `CLAUDE.md` 工作说明。
3. `docs/00-product-requirements.md`。
4. `docs/04-security-privacy-spec.md`。
5. 其他 `docs/` 标准文件。
6. 当前代码实现。

安全和隐私规则优先级高于便利性。

## 7. 推荐开发节奏

建议每次只做下列之一：

- 一个窗口骨架。
- 一个 Tauri 命令。
- 一个系统集成能力。
- 一个设置项。
- 一个 AI 调用链路。
- 一个验收修复。

不要把多个核心能力混在一次开发里。

## 8. 安全审计

发布前必须执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts\security-audit.ps1
```

脚本会依次执行：

- `pnpm --filter quickpick-desktop audit --prod`
- `cargo audit`

如果本机未安装 `cargo-audit`，先执行：

```powershell
cargo install cargo-audit
```

仓库同时提供 `.github/workflows/security-audit.yml`，在 push、PR 和每周计划任务中运行 npm 与 Rust 依赖审计。高危漏洞不允许进入 release。

## 9. 收尾说明

每次回复用户时应简要说明：

- 做了什么。
- 修改了哪些关键文件。
- 如何验证。
- 下一步建议。

如果有检查没跑，必须说明原因。
